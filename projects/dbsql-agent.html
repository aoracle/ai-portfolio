Databricks SQL Agent

A schema-aware natural-language SQL agent that turns plain-English questions into safe, optimized queries against a relational warehouse — with structured LLM output, hard safety guardrails, and an introspection layer that ingests the live schema instead of pretending it knows it.

Schema-Aware Prompting Read-Only Guardrails Structured JSON Output Conversational Memory Pluggable Warehouse

Every "ChatGPT for your database" demo I've watched falls apart the same way: the LLM hallucinates a column, the user runs the query, the warehouse charges them for a full table scan, and somebody's dashboard quietly turns into a lie. I built this agent to be the opposite of that demo. It pulls the schema from information_schema at startup, hands the LLM a structured map of every table, column, foreign key, and view, forces a JSON-shaped response so I can validate before execution, and refuses anything that isn't a SELECT or WITH. The reference implementation runs against a PostgreSQL warehouse holding a real-world museum/gallery schema (53 tables, foreign-key-rich). The same architecture drops onto a Databricks SQL warehouse with no change to the agent loop.

The Problem I Was Solving

On the BAMPFA project I had a curator who could describe what she wanted — "show me every film by Kurosawa we've screened in the last three years, grouped by venue" — but no SQL. Her alternatives were waiting on a developer, navigating a Tableau cube someone built two years ago, or living without the answer. I wanted a fourth option: she types the question, the agent writes the SQL against the real schema, executes it read-only, and shows her the result with a plain-English explanation of what just happened.

The hard parts aren't the LLM. The hard parts are the things people skip in demos: (1) the model needs the actual schema, not a hand-written summary that drifts out of sync; (2) the model will absolutely write a DELETE if you don't physically stop it; (3) the response has to be parseable so my code can act on it — not a free-text essay; (4) when the LLM hallucinates a column name (and it will), the failure has to surface as a clean error message, not silent wrong data.

System Architecture

Four components, each replaceable. The agent loop is deliberately boring — the intelligence lives in the prompt and the schema context, not in framework magic.

┌─────────────────────────────────────────────────────────────────┐
│  User  (CLI / API / Streamlit)                                  │
│    "Which curators have worked on the most exhibitions?"        │
└─────────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────────┐
│  SQLAgent  (LangChain + ChatOpenAI, temperature=0.1)            │
│    1. Build system prompt = schema context + safety rules       │
│    2. Append last 4 turns of conversation history               │
│    3. Call LLM, demand JSON: {query, explanation, reasoning}    │
│    4. Parse JSON; fall back to SQL extraction if malformed      │
└─────────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────────┐
│  Safety Gate  (settings.is_query_safe)                          │
│    • Must start with SELECT or WITH                             │
│    • Must NOT contain DROP/DELETE/UPDATE/INSERT/ALTER/CREATE    │
│    • Rejects before the query ever touches the warehouse        │
└─────────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────────┐
│  DatabaseManager  (SQLAlchemy, pool_pre_ping, schema-scoped)    │
│    • SET search_path TO <schema> on every connection            │
│    • Execute, cap rows at max_query_results                     │
│    • Return DataFrame + row count + execution time              │
└─────────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────────┐
│  Schema Introspection  (cached, lazy)                           │
│    • Reads information_schema.tables / .columns / .key_*        │
│    • Builds {tables, columns, foreign_keys, views} dict         │
│    • Renders into a markdown system-prompt block                │
└─────────────────────────────────────────────────────────────────┘

The non-obvious decision: schema introspection runs once at startup, gets cached on the agent, and is re-rendered into the system prompt on every call. The LLM never sees the warehouse directly — it sees a structured markdown view of the warehouse that my code generated from live metadata. If a column is added tomorrow, restart the agent and the new column shows up in the prompt with no code change.

Component 1 — Schema Introspection

This is the foundation. The agent is only as smart as the schema context it gets. I read three information_schema views — tables, columns, and the join across table_constraints / key_column_usage / constraint_column_usage for foreign keys — then assemble them into a single nested dict that gets rendered into the LLM's system prompt.

fk_query = text("""
    SELECT
        tc.table_name,
        kcu.column_name,
        ccu.table_name AS foreign_table_name,
        ccu.column_name AS foreign_column_name
    FROM information_schema.table_constraints AS tc
    JOIN information_schema.key_column_usage AS kcu
        ON tc.constraint_name = kcu.constraint_name
    JOIN information_schema.constraint_column_usage AS ccu
        ON ccu.constraint_name = tc.constraint_name
    WHERE tc.constraint_type = 'FOREIGN KEY'
    AND tc.table_schema = :schema_name
""")

That last join — foreign keys — is the secret sauce. Without it, the LLM has no idea that event_speakers.person_id relates to persons.id. With it, the LLM writes correct JOINs on the first try. I render the FKs into the prompt with arrow notation the model parses natively:

### event_speakers
Purpose: Maps speakers to events
Columns:
  - id: integer (not null)
  - event_id: integer (not null)
  - person_id: integer (not null)
  - role: varchar (nullable)
Foreign Keys:
  - event_id → events.id
  - person_id → persons.id

The same approach works against Databricks SQL: Unity Catalog exposes the equivalent metadata via system.information_schema.tables, columns, and constraint_column_usage. Swap the connection string and the SQL dialect of the introspection queries; the agent loop doesn't change.

Component 2 — Structured LLM Output

I refuse to parse free-text responses. The system prompt demands JSON with three fields: query, explanation, reasoning. The LLM gets temperature 0.1 to stay deterministic. If the JSON parse fails, I have a fallback that extracts the first SELECT ... ; block from the text — but I treat the fallback as a smell and log it.

try:
    response_data = json.loads(response.content)
    query = response_data.get('query', '').strip()
    explanation = response_data.get('explanation', '')
    reasoning = response_data.get('reasoning', '')
except json.JSONDecodeError:
    # Fallback: best-effort SQL extraction
    content = response.content
    if 'SELECT' in content.upper():
        lines, in_query, query_lines = content.split('\n'), False, []
        for line in lines:
            if 'SELECT' in line.upper() or in_query:
                in_query = True
                query_lines.append(line)
                if line.strip().endswith(';'):
                    break
        query = '\n'.join(query_lines).strip()
        explanation = "Query extracted from response"
        reasoning = "Fallback parsing used"

Why bother with the fallback? Because LLMs occasionally wrap JSON in markdown code fences, hallucinate a leading sentence, or drop a trailing comma. I'd rather degrade gracefully than throw on a glitch. But every fallback is a signal that the prompt needs to be tightened.

Component 3 — The Safety Gate

This is the smallest piece of code in the system and the one I trust most:

def is_query_safe(self, query: str) -> tuple[bool, Optional[str]]:
    query_upper = query.upper().strip()

    # Reject anything containing a blocked keyword
    for keyword in self.blocked_keywords:    # DROP DELETE UPDATE INSERT ALTER TRUNCATE CREATE
        if keyword in query_upper:
            return False, f"Blocked keyword detected: {keyword}"

    # Must start with SELECT or WITH
    starts_with_allowed = any(
        query_upper.startswith(op) for op in self.allowed_operations
    )
    if not starts_with_allowed:
        return False, f"Query must start with one of: {', '.join(self.allowed_operations)}"

    return True, None

Three lines of real logic. No regex, no SQL parser, no clever AST analysis — just a substring check and a startswith check. This works because the layer behind it is also read-only by configuration: the warehouse user the agent connects with does not have write privileges. The gate is defense-in-depth, not the only line of defense.

Critically, the safety check runs before the query reaches the database driver. A query that fails the gate never opens a transaction, never bills compute, never appears in the warehouse audit log as a rejected statement. It's free.

Component 4 — Conversational Memory

The agent keeps the last 4 turns of conversation history in a ring buffer. This is what lets the user say "now group that by year" instead of restating the entire question. Token budget matters — I cap history at 10 messages and drop the oldest when the buffer fills:

self._conversation_history.extend([human_message, response])
if len(self._conversation_history) > 10:
    self._conversation_history = self._conversation_history[-10:]

Schema context, on the other hand, lives in the system message every turn — it never rolls off. The user's follow-up always has the full schema in scope, regardless of how long the conversation runs.

Component 5 — Execution and Result Shaping

The database manager uses SQLAlchemy with pool_pre_ping (cheap liveness check) and pool_recycle=300 (drop stale connections). Every query runs inside a connection block that first sets the search path to the configured schema — so the LLM doesn't need to qualify every table name with the schema prefix, keeping the generated SQL clean and portable.

with self.engine.connect() as conn:
    conn.execute(text(f"SET search_path TO {settings.db_schema}"))
    result = conn.execute(text(query))

    if result.returns_rows:
        df = pd.DataFrame(result.fetchall(), columns=result.keys())
        if len(df) > settings.max_query_results:
            df = df.head(settings.max_query_results)
            warning = f"Results limited to {settings.max_query_results} rows"
            return True, df, warning
        return True, df, None

Results come back as a pandas DataFrame, capped at max_query_results (default 100) so a missing LIMIT in an aggregation against a million-row table doesn't blow up memory. The CLI surface uses rich to render the DataFrame as a syntax-highlighted SQL block plus a result table — the demo experience matters because this is how I convince non-technical stakeholders the agent is real.

Component 6 — Explain and Suggest

Two side-features that punch above their weight: explain_query() takes an arbitrary SQL string and returns a plain-English description (useful when a developer wants to understand someone else's query), and suggest_similar_queries() takes the user's question and returns 3-5 follow-up questions. The suggestion feature is the one curators actually use — it turns the agent from a one-shot tool into a guided exploration session.

def suggest_similar_queries(self, question: str) -> List[str]:
    system_message = SystemMessage(content="""
    Based on the museum database schema and a user's question,
    suggest 3-5 similar questions they might want to ask.
    Focus on: related data exploration, different perspectives,
    common analytical questions, questions that build on the current one.
    Return suggestions as a simple list, one per line.""")

    human_message = HumanMessage(
        content=f"User asked: {question}\n\nSuggest similar questions:"
    )
    response = self.llm([system_message, human_message])
    return [
        line.strip().lstrip('•-*').strip()
        for line in response.content.split('\n')
        if line.strip() and not line.startswith('#')
    ][:5]

Why It Works

Five design choices keep the agent honest:

  1. Live schema beats hand-written context. The LLM is reading the warehouse as it exists right now, not a frozen description in a markdown file that someone forgot to update three sprints ago.
  2. Structured JSON output beats freeform parsing. When I demand {query, explanation, reasoning}, I can validate, log, and route each field independently. The explanation lands in the audit trail; the query goes to the safety gate.
  3. Layered safety. Keyword denylist at the application layer, read-only credentials at the warehouse layer, result-row cap at the result layer. Three independent failures would need to align for damage.
  4. Foreign keys in the prompt. The single biggest accuracy lift came from rendering FK relationships into the system prompt. Without them, the LLM guesses joins; with them, it gets them right.
  5. Conversation memory in the user channel, schema in the system channel. The schema is non-negotiable context; the conversation is best-effort context. Keeping them in different message types means I can prune the latter without touching the former.

What I Learned

The first-principles lesson: the LLM is the cheapest, least reliable part of the system. Everything that makes this agent trustworthy — the schema introspection, the JSON validation, the safety gate, the connection pooling, the row caps — is plain engineering. The LLM is a translator. Treat it like a translator, not an oracle, and the system becomes predictable.

The second lesson: structured output is the difference between a demo and a product. The first version of this agent returned free text and I parsed it with regex. It worked 85% of the time. Switching to a strict JSON contract pushed it to 99%, because now the failure mode is "JSON parse error" — loud, logged, easy to debug — instead of "we silently dropped the WHERE clause."

The third lesson: schema-aware prompting generalizes. The exact same architecture — introspect the catalog, render foreign keys, force JSON, gate the output — runs against Postgres, against Databricks SQL with Unity Catalog, against Snowflake. The warehouse swap is a SQLAlchemy URL change. The agent's intelligence is in the prompt construction, not the database driver.

Tech Stack

Python 3.11. LangChain (ChatOpenAI, HumanMessage, SystemMessage) for the LLM client. OpenAI GPT-4 Turbo, temperature 0.1. SQLAlchemy with connection pooling (pool_pre_ping, pool_recycle=300). PostgreSQL 16 in the reference implementation; portable to Databricks SQL via Unity Catalog. Pydantic BaseSettings for typed config. typer + rich for the CLI (syntax-highlighted SQL, tabular results, panel layouts). pandas for result DataFrames. Optional FastAPI + Streamlit surfaces in the docs folder for HTTP and demo UI.
