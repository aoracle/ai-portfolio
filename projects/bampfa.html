BAMPFA — Custom CMS for UC Berkeley's Art Museum

A 12-month engagement replacing a working museum's FileMaker + Drupal 7 tangle with a single Flask + PostgreSQL content system — live in production today, modeling 15 entity relationships and the full film-booking workflow that runs the institution's programming.

Live in Production 71 Tables · 15 Entity Relations PostgreSQL 16 Flask + Gunicorn Iterative CMS Build

BAMPFA — the Berkeley Art Museum and Pacific Film Archive — is a working museum and film archive whose programming data lived for years in disconnected FileMaker databases and a Drupal 7 website that didn't talk to each other. I was brought in as the data architect to replace that with one system. Twelve months later it is a custom Flask + PostgreSQL CMS running live on a Digital Ocean VPS: the FileMaker replacement, 71 tables modeling 15 entity relationships, and the full booking/payment workflow the film team now operates against. The codebase has been delivered to the client's own repository, and the film team begins testing with real data in mid-2026. This is that system — how it's built, what changed mid-build, and what I learned doing it.

The Problem I Was Solving

Three systems, none of them talking. FileMaker held the internal booking logistics — which films are booked, what's owed to distributors, shipping, condition reports. Drupal 7 held the public website. CollectionSpace/CineFiles held the film-archive metadata, and Tessitura handled ticketing. Staff duplicated data across systems by hand, reporting was a spreadsheet exercise, and none of it was auditable. The museum needed one source of truth.

The harder problem was that no one could fully spec it on paper. A museum's data model is deeply interconnected: a single screening event touches a film (with title variations, credits, countries, languages), a series, a venue, guest persons (with bios and roles), and a booking record (with payments, shipping, condition reports). Until the team could click through real forms, no one knew that countries needed to be multiselect tags instead of a dropdown, or that payment blocks needed to be tied to specific screening dates. CMS requirements emerge when real users touch real software — I planned the project around that fact from day one, in feedback rounds, instead of pretending the spec could be frozen upfront.

System Architecture

A Flask web application served by Gunicorn behind Nginx, on a single Digital Ocean VPS running Ubuntu 24.04. PostgreSQL 16 holds everything in one normalized schema. The shape is deliberately hub-and-spoke: core entities — films, events, series, bookings, persons, venues — connect through junction tables that carry the relationship semantics (role, billing order, primary flag, display order). The junction layer is where the actual work lives; the entity tables are almost the boring part.

The numbers, as of the last accounting: 71 tables, 32+ database views exposing them to the UI, 61 performance indexes, 121 API routes, roughly 2,700 lines of Python. Six entity forms, each with full create / edit / search. The booking module is the heart of the system and the part that actually replaces FileMaker — a booking has a type (exhibition vs. permission), linked pairs (bidirectional), distributor contact notes with snapshots preserved at booking time, condition reports, shipping records, and multiple payment blocks each tied to specific screening dates.

The Hard Part — Entity Linking

The single largest engineering effort on the project was making every entity connect to every other entity. This is what turns the CMS from a data store into something useful for daily work. Fifteen junction relationships: Series↔Events, Events↔Films (with drag-drop screening order), Events↔Persons (roles, bios), Films↔Credits (director, actor — drag-drop ordering), Films↔Title Variations, Films↔Countries/Languages (multiselect tags), Films↔Related Films, Persons↔Name Variations, Persons↔Bios, Bookings↔Screenings, Bookings↔Payments, Bookings↔Linked Bookings, and the rest. Each one required database tables and views, GET/POST/PUT/DELETE endpoints, JavaScript for the UI, and integration into the form templates — 60+ endpoints just for linking. Autocomplete search walks the alias tables, so "Tarkovsky" finds "Andrei Tarkovskiy" and the original Russian spelling. Search is the daily workflow; it has to be forgiving.

The Payment Redesign (where the structure changed mid-build)

Six months in, the museum's testing lead flagged that payment data was scattered across three flat cards and Accounts Payable rows hung off the booking with no structure. This became structural priority #1. The redesign collapsed it into one Payment Information area: overall terms at the top, then multiple payment blocks each tied to a screening, with AP rows — date, amount, currency, invoice, note — nested inside each block with inline add / edit / delete. A migration added a nullable foreign key with ON DELETE CASCADE, so deleting a block cleans up its AP rows automatically. Shipped, tested, deployed to production.

This is the canonical example of the thing I planned for: a change you cannot spec on paper, because it only surfaces when a tester uses the real form and feels the friction. It is also the kind of change that, done right, makes the system permanently more honest — payment data now models how the museum actually thinks about money, not how FileMaker happened to store it.

The Build Cycle (honest version)

CMS work is iterative and I treated that as the method, not as scope creep. Round one: after the initial build, the testing lead produced a 66-item feedback document — 22 quick fixes, 12 medium features, 8 complex features (inline "Create New" modal, a Manage Lookups admin page, payment blocks, linked bookings). All 62 actionable items shipped; the rest were deferred on real decisions, not on effort. Round two: another testing pass, another set of fixes. Round three (mid-2026): the payment redesign above, plus three sent-back items — condition-report edit/delete failing in Safari, collapsible sections that would open but not close, distributor contact notes stuck on "Loading." All fixed and deployed. The codebase was delivered clean to the client's own Berkeley repository (no internal files, no secrets, single signed commit), and the film team is queued up to test with real data.

Why It Works — Design Decisions

  1. One schema, no migrations. The deployment strategy versions schemas by timestamp and deploys clean DDL instead of mutating state in place. There is no migration drift, and "what state is prod in?" is a question that never comes up — the schema name is the answer.
  2. Entity linking as a first-class concern. Fifteen junction tables, each carrying real semantics (role, order, primary flag). The CMS is not a CRUD app; it is a relationship graph the UI exposes. That is the whole reason it can replace FileMaker.
  3. Booking snapshots preserve history. Distributor contact info is copied onto the booking at creation time. Years from now, when the distributor's address changes, the old booking still shows what was true when it was made. This is the difference between a database and a record-keeping system.
  4. Lookups are admin-managed. Countries, languages, roles, formats, pricing categories — all editable from a Manage Lookups page with no SQL required. The team is never blocked on me to add a value.
  5. Autocomplete across aliases. Person and film search walks the alias tables, so variant spellings and original-language titles resolve. The museum catalogs international film; search has to meet that bar.
  6. Built for the decade, not the demo. Naming conventions, relationship patterns, audit tables, and snapshot preservation are the foundation everything downstream rests on. Getting them right during the build is far cheaper than fixing them after years of data entry.

What I Learned

The headline lesson: you cannot fully spec a CMS on paper. You can put the best architect in the room and it will not matter — until a tester clicks through a real form, neither they nor you know that payment blocks need to be tied to screening dates, or that countries need to be multiselect tags instead of a dropdown. These are not missed requirements; they are discoveries that only surface in contact with running software. I planned the project in feedback rounds, and every round produced 15–25 hours of valuable refinement. Treating that as scope creep instead of as the core method would have produced a worse system, faster.

The second lesson: in a deeply interconnected data model, every UI change has a blast radius. A single screening touches film, series, venue, persons, and bookings. Changing how one entity's form behaves often forces changes across three others. I learned to map the relationship blast radius before touching a form, not after — the diagram is the cheapest debugging tool on a project like this.

The third lesson, the one I care about most: build for the decade, not the demo. The decisions made during the build — naming, relationship patterns, audit trails, snapshot preservation — set the ceiling for everything that follows. A sloppy foundation is invisible in the demo and expensive for years. The boring integrity work (audit tables, foreign-key constraints, snapshot copies, alias search) is precisely what makes this a system the museum can run on, rather than a prototype that impresses once.

Tech Stack

Flask (Python) served by Gunicorn behind Nginx on a Digital Ocean VPS running Ubuntu 24.04. PostgreSQL 16 holds a single normalized schema of 71 tables, 32+ views, and 61 indexes. The frontend is vanilla JavaScript plus HTML templates — no framework, because the forms are the product and a framework would have added build steps without adding capability. Daily automated backups. The system is live, and the client owns the code in their own Berkeley repository.
