Custom Claude Infrastructure

A persistent memory system, a custom tooling layer, and an education layer built on top of Claude — so it remembers across sessions, integrates with my actual workflow, and scales with me instead of resetting every time.

Persistent Memory Cross-Session Continuity File-based, Markdown-driven Multi-machine tmux + Slash Commands

Claude is good out of the box. It is not enough for the way I actually work. I run multiple consulting engagements, a personal trading book, several family-side projects, and an interview pipeline — all in parallel, all across four machines. Every chat starts at zero unless I do something about it. So I built three layers on top of Claude: a memory system that survives a reboot, a tooling layer that gives me one keystroke to spin up a coordinated team of agents in tmux, and an education layer that became my own first-principles textbook on the Anthropic API. Together they turn Claude from a clever text box into a piece of infrastructure I depend on daily.

The Problem I Was Solving

Out of the box, every LLM session is a goldfish. You teach it your codebase, your domain, the seven rules you don't want it to violate, the three projects in flight, the way you like your code formatted — and then you close the tab and it forgets all of it. The next morning you start over. Multiply that by the number of projects I touch in a week and the loss compounds: hours per day re-establishing context, plus the much larger cost of decisions I made yesterday that today's session never learns about.

I tried the obvious things first. Long system prompts — ballooned and rotted. One giant CLAUDE.md per project — better, but still dumb: it reloaded every time and couldn't represent "this is a hard rule I learned the hard way on April 22nd" differently from "this is a one-time project note." And it didn't help me bring up multiple Claude sessions side by side when I needed three coordinated agents (one watching the tape, one writing code, one summarizing) instead of one chat.

So I split the problem into three layers, each with a single responsibility, and built one folder for each. The result is the system below.

System Architecture

Three independent repositories, three responsibilities, all reachable from any Claude session running anywhere in my codebase. Memory is files on disk. Tooling is shell scripts and a slash command. Education is a runnable Python course I wrote to force myself to understand the API at the protocol level before relying on it.

The three folders are deliberately independent. Memory can be wiped without breaking the tools. Tools can be reinstalled without touching memory. The tutorial is read-only reference and never writes. This is the same trust-boundary discipline I use for production systems: one folder, one job, fail in isolation.

Component 1 — claude-memory (the persistent brain)

Memory is the most important of the three because everything else assumes it. The design is intentionally boring: a flat folder of markdown files, an index file that names them, and a frontmatter schema that lets Claude tell at a glance what kind of memory each file is.

The index, MEMORY.md, lives at the root. It is the first thing Claude reads at session start. The top section is labeled READ FIRST and points at the master strategy file, the hard-rules file, and the behavioral frame for the current project. The middle section is a chronological index of every persistent memory file with a one-line hook describing what it contains. New files get appended to the bottom; nothing is ever deleted.

# MEMORY.md (excerpt — the index)

## ★ READ FIRST at session start
- memory/strategy_master.md      — the consolidated playbook
- memory/rules_hard_constraints.md — DO/DON'T list, 30-sec scan
- memory/user_roles_and_modes.md   — behavioral frame

## Persistent Memory Files
- memory/feedback_never_delete_data.md  — empirical data is the gold
- memory/feedback_dont_overengineer.md  — most problems are one-line fixes
- memory/feedback_discuss_dont_conclude.md — explore, don't ship by default
- memory/feedback_plan_before_large_changes.md — plan file, approve, then ship
- memory/project_YYYY-MM-DD_session.md   — end-of-day session log
- ...

Every memory file carries frontmatter so it self-describes. The schema is deliberately small: a name, a description, a type (one of feedback, project, strategy, rules, user, or reference), and a session ID that traces the file back to the conversation where the lesson was learned.

---
name: Never delete or overwrite accumulated data — it's the gold
description: Hard rule. Empirical data is the product itself. Append-only.
type: feedback
originSessionId: 22038f82-9417-46bd-84b4-e75c70004e7e
---

Empirical data we capture is the product itself — the gold being mined.
Never design schemas, scripts, or features that wipe, truncate, or
apply retention policies to this data.

**Why:** The value compounds with accumulated history...
**How to apply:** Default to INSERT ... ON CONFLICT DO UPDATE...
**Related rule:** Global CLAUDE.md "NEVER DELETE FILES" extends to data.

The type tag is doing real work. A feedback file represents a rule I taught Claude after it got something wrong — it should be loaded into every session and treated as a constraint. A project file is end-of-day state for a specific build — load only when that project is active. A strategy file is a playbook I want consulted before any related action. A rules file is a 30-second scannable DO/DON'T list. The same folder serves all of these because the type tag tells the reader how to weight each file.

End-of-day discipline is built in. After any meaningful work session, Claude appends a new project_YYYY-MM-DD_session.md file with frontmatter, a "ship list," any rules locked in that day, and a 3-5 line resume block for the next session. The next morning's Claude reads the most recent session file and inherits the full state in under two seconds. 365 of these in a year is fine. They are append-only build history.

The first principle behind all of this: memory is not state, it is documents. Documents don't need a database, don't need a server, don't need an API. They sync via Dropbox, they grep with ripgrep, they diff with git, and they outlive any vendor.

Component 2 — claude-tools (the tooling layer)

One Claude window is not enough when the work has multiple concurrent roles. While debugging a trading-system pipeline, I want one Claude watching the tape, one writing Python, one summarizing the day, and one acting as the discipline layer that refuses to let me trade against my own rules. Each one needs its own working directory, its own slash command, its own visual identity so I don't confuse them, and its own tmux window so I can flip between them with one keystroke.

That is what claude-tools does. It is a small repository of shell scripts and Claude slash commands that turn a tmux session into a coordinated multi-agent environment.

The flagship piece is the /tmuxpro skill. It is a Claude Code slash command that walks me through setting up a multi-window tmux environment for any project. It asks how many agent windows and script windows I need, assigns colors from a fixed palette, and generates the config files, the launcher script, and the per-project /crew command that spins everything up later in one shot.

# crew.conf — agent definitions for one project
# name | command   | label       | color    | bg_tint  | directory
researcher|/research|Researcher  |#00bfff   |#0a1a2a   |agents/researcher
coder     |/code   |Coder        |#00ff87   |#0a1f0a   |agents/coder
reviewer  |/review |Reviewer     |#ffd700   |#1f1a0a   |agents/reviewer
discipline|/enforce|Discipline   |#ff4500   |#1f0a00   |agents/discipline

The crew-launcher script reads that file and opens one tmux window per agent, each with its color, background tint, working directory, welcome banner, and auto-submitted slash command. The cyan window is the researcher. The green window is the coder. The red window is the discipline layer that says "no" to me. I never have to remember which window is which — the color tells me, before I read a single line.

Alongside the agent launcher is a parallel script-launcher for non-Claude windows — the market-data monitor, the log tail, the cron watcher. Same config-file convention, different content, no Claude in those windows. The point is that the same visual+keyboard discipline applies whether the window holds an LLM or a tail -f.

The tmux config that ships with the installer is opinionated. The prefix is Ctrl+A instead of Ctrl+B. Splits are | horizontal and - vertical. Pane navigation is Option+Arrow with no prefix. F1 through F12 jump directly to windows 1-12 with no prefix. Mouse support is on, base index is 1, scrollback is 50,000 lines, and 256-color plus true-color are enabled. Every one of those choices came from a real friction point I hit running multi-agent setups.

There is also an identity/ folder — three markdown files (IDENTITY.md, SOUL.md, USER.md) that any headless Claude invocation can be pointed at to establish who it is, what it is allowed to do, and who I am to it. This is what lets me run claude -p "..." non-interactively from a script and still have it behave like the same coherent agent across calls.

Installation is one command:

git clone <repo>/claude-tools.git ~/claude-tools
bash ~/claude-tools/install.sh
# — copies /tmuxpro skill to ~/.claude/commands/
# — backs up any existing ~/.tmux.conf, installs the recommended one
# — reloads tmux config if currently inside tmux

After that, every project gets its own coordinated crew with one command. The slash-command pattern means I never have to remember the shell incantation — Claude itself drives the setup.

Component 3 — claude-tutorial (the education layer)

I am suspicious of tools I use heavily but understand only superficially. The Anthropic API is one of those tools. So I built a runnable, interactive tutorial — eight chapters, real API calls, quizzes after each chapter — as a way to force myself to learn it at the protocol level. The tutorial lives in claude-tutorial/ and doubles as reference material when I am building something new.

The curriculum maps the Anthropic API at increasing depth:

  • Chapter 1 — First API request. Anatomy of the response object, role of messages, what stop_reason actually means.
  • Chapter 2 — Multi-turn conversations. Managing history, alternating roles, the cost of dragging context.
  • Chapter 3 — Helper functions. Wrapping the SDK so I never have to remember the verbose calling convention.
  • Chapter 4 — A working chat application built from the helpers.
  • Chapter 5 — System prompts. Constraint vs. personality vs. format scaffolding, and when each matters.
  • Chapter 6 — Temperature. Empirical demonstrations of how 0.0, 0.5, and 1.0 change the same prompt's output distribution.
  • Chapter 7 — Streaming. The event types, how to assemble a response incrementally, why streaming changes UX.
  • Chapter 8 — Output control. Prefilled assistant turns and stop_sequences as the cheapest steering knobs available.

The architecture mirrors how I learn: a thin core/ module (client, conversation manager, image helper, quiz engine) sits underneath chapter files that import from it. Each chapter is a runnable Python module with live code examples and ASCII art for the diagrams. The main.py entry point sequences the chapters with quizzes between them; anthropic_api_tutorial.py is a single-file version for people who just want to read.

# core/client.py — the wrapper every chapter imports

class ClaudeClient:
    """Thin wrapper around anthropic.Anthropic with sane defaults."""

    def __init__(self, model="claude-sonnet-4-5", max_tokens=1024):
        self.client = anthropic.Anthropic()  # picks up ANTHROPIC_API_KEY
        self.model = model
        self.max_tokens = max_tokens

    def ask(self, prompt, system=None, temperature=1.0):
        kwargs = dict(
            model=self.model,
            max_tokens=self.max_tokens,
            temperature=temperature,
            messages=[{"role": "user", "content": prompt}],
        )
        if system:
            kwargs["system"] = system
        return self.client.messages.create(**kwargs).content[0].text

Building it taught me three things I now use every day. First, the API's surface is small — most of the apparent complexity is in how you compose messages, not in the API itself. Second, system is a much sharper steering tool than a long user prompt; once I internalized that, my own production prompts shrank by half. Third, streaming and stop sequences are wildly under-used — they are the cheapest UX upgrades available and most people skip them because the docs frame them as advanced.

The tutorial is also the seedbed for the helpers that ended up in the tooling layer. The headless invocation pattern in claude-tools/identity/ is a direct descendant of Chapter 5's system-prompt experiments.

How the Three Layers Interact

The three folders look independent but they reinforce each other in a way that I only noticed after living with them for a few months:

  1. Memory makes tools coherent. When the crew launcher spins up four Claude windows for a project, all four read the same CLAUDE.md and the same memory/ folder. They start the morning with shared context. The "discipline layer" agent and the "coder" agent reference the same hard rules — there is no possibility of them disagreeing on policy.
  2. Tooling makes memory portable. The tmux/skill installation pattern means every machine I own can recreate the same multi-agent environment in one command. Combined with Dropbox-synced memory, a fresh machine is productive in under five minutes.
  3. Education makes both honest. When something in the memory or tools layer behaves surprisingly, the tutorial is where I go to reproduce it minimally and figure out whether the surprise is mine or the API's. Most of the time it's mine.

Why It Works — Design Decisions

  1. Files, not state. Every persistent artifact is a flat file. No database, no server, no API to maintain. grep, git, and Dropbox are the entire infrastructure. The system survives any vendor outage.
  2. Frontmatter as a type system. A two-line YAML header per memory file is enough metadata for Claude to weight feedback rules differently from project notes differently from strategy playbooks. Almost free, hugely useful.
  3. Append-only memory. Nothing is ever deleted. End-of-day session files accumulate. The compounded history is more valuable than any "tidy" current state would be. I learned this from the trading data: a single day is noise, a year is a dataset.
  4. One slash command per workflow. If I have to remember a shell incantation, I will forget it. If it is a Claude slash command (/tmuxpro, /crew), Claude itself reminds me. The cost of building the skill once is repaid every time I open a project.
  5. Visual coding for parallel agents. Color is bandwidth. A red window and a cyan window communicate role faster than any title bar. The tmux color palette is the cheapest UX upgrade in the whole stack.
  6. Education before reliance. Writing the tutorial before I built the tools meant the tools were built on actual understanding, not vibe coding. The 60 hours of writing chapters has paid for itself 10x in not-shipping-broken-prompts.

What I Learned

The first principle that drove all of this: information doesn't need activation, it just needs to be available. Every "smart memory" startup wants to add a vector database and a recall layer. I tried it. None of it beat a flat folder of markdown files that Claude reads at session start. The cost of the markdown approach is near zero; the ceiling is whatever I can stuff into a CLAUDE.md plus what Claude can grep on demand. That is enough for everything I actually do.

The second lesson: tools should be slash commands, not shell aliases. The moment I moved my multi-agent setup from a shell script I had to remember to a /tmuxpro slash command Claude could discover, my actual usage of it went up 5x. Discoverability is a feature, and Claude itself is the best place to put it.

The third lesson, the hardest one: the system has to be boring before it becomes valuable. The first three versions of the memory layer had clever indexing, fuzzy matching, an embedding cache. None of it helped. The current version has a flat folder, an index file, and frontmatter tags. It is so simple that there is nothing to break. That is exactly why I trust it.

Tech Stack

Markdown for memory. YAML frontmatter for type tagging. Bash for installers and launchers. tmux 3.x with a custom ~/.tmux.conf. Claude Code slash commands for discoverability. Python 3 for the tutorial (uses the official anthropic SDK). Dropbox for cross-machine sync. ripgrep for memory search. Git for version history. No databases. No servers. No build steps.
