Gajadata Life-OS

A personal operating system — a static dashboard PWA installed on my iPhone home screen, a markdown queue on a $6/mo VPS, a 15-minute AI cron on a private Mac, and a mesh-VPN sync layer tying four machines into one system that routes voice notes into project folders without me touching a keyboard.

HTTPS PWA iPhone Home Screen 3-Plane Architecture 15-min AI Cron Daily Backup + KB Export

This is the wrapper around everything else I build. A meeting note, a recruiter email, a project task, a family reminder — they all enter the same input surface (the Quick Notes card on a PWA I have pinned to my phone), get pulled by a 15-minute cron running Claude on a private Mac, and land as routed markdown files in the correct project folders. Four machines stay in sync. The dashboard, the queue, and the iPhone app all run on a $6/month VPS. The whole system is three static HTML files, two Python scripts, one shell script, one markdown queue, and a service worker. No database, no message bus, no framework. It is the most useful thing I have built and also the dumbest, and that is the point.

The Problem I Was Solving

Personal infrastructure has a Goldilocks problem. On one side are SaaS apps (Otter, Notion, Todoist, TickTick, Apple Notes) — each is a polished island, none of them talk to each other, and the corpus lives behind an account I don't control. On the other side is “build a full-stack app” — React, Postgres, Auth0, a worker queue, deploys — which is grotesque overkill for one user and his own notes. Neither end of the spectrum fit.

I wanted three things at once: (1) one input surface from my phone, ideally one tap from the lock screen; (2) smart routing that knew the difference between a client work note, a family item, a job-search thread, and a side-project todo, and filed each in the right place without me picking a folder; and (3) ownership — the corpus as plain markdown on disk, synced across my machines, in folders I control. Plus a constraint: it had to be cheap enough to forget about. Six dollars a month, not sixty.

The VPS serves the dashboard and holds a markdown queue. The private Mac runs Claude on a cron and pulls from that queue. The iPhone submits via a PWA. Dropbox plus a mesh VPN keep four machines in sync. No service in the path costs more than the VPS itself.

System Architecture

Three planes, each with a clear job. The public plane is the VPS — hardened nginx serving static HTML and one PHP endpoint that accepts new notes. The private plane is a Mac on a mesh VPN — it pulls the queue, runs Claude with a routing prompt, and writes routed files into the project tree. The sync plane is Dropbox plus a small daily rsync job — it propagates those files to every other machine and backs them up externally. Two cron jobs on the Mac (a 2 AM backup and a 2:30 AM Claude-conversation export) round out the daily cycle.

The iPhone POSTs into a markdown queue on the public VPS (Plane 1, accent). The private Mac (Plane 2, dark) pulls that queue over a mesh VPN every 15 minutes and routes via Claude. The sync layer (Plane 3) propagates the routed files back out to every machine and to an external backup. No plane trusts the others with credentials; the only thing crossing each boundary is markdown.

Component 1 — The Public VPS (input surface + dashboard)

A $6/month cloud droplet running nginx over Let’s Encrypt TLS, fronted by HTTP basic auth. It serves two things. First, the dashboard itself: static HTML, a manifest.json for the PWA install, an icon set, a service worker. Second, one PHP endpoint (/api/notes.php) that accepts a POST from the Quick Notes card and appends one line to /queue/notes.md on disk. That's it. There is no database, no auth system beyond the basic-auth password, no framework, no JavaScript runtime. The queue is a text file.

The choice of PHP is deliberate and a little heretical in 2026. The endpoint does one thing (append a sanitized line to a file). PHP is already installed on every blank Ubuntu droplet's nginx; there is nothing to deploy, nothing to supervise, nothing to restart on crash. A Node or Flask app would have meant a process manager, a port, a reverse-proxy stanza, and a memory footprint — for one string-concat. PHP wins on first-principls here.

Component 2 — The Private Mac (the routing brain)

An always-on Mac on the same mesh VPN as nothing else public. It has no open inbound ports. The 15-minute cron reaches out to the VPS, pulls queue/notes.md to a local copy, bails if it's empty (don't burn tokens), and otherwise hands the queue to claude -p with a routing prompt. On success it clears the remote queue. Pull, never push.

The prompt is a markdown file (PROMPT.md) I can edit in 30 seconds without redeploying anything. It encodes the noise filter (Plaud records continuously; 70% of any transcript is café chatter), the project classifier (a keyword table interpreted by Claude so “Cap Group” routes the same place as “Capital Group”), and the name dictionary that fixes recurring transcription errors. The output lands in two places for every note: the project folder that matched, and a central chronological voice log under ANAND/notes/voice/. The double-write means I can grep the central log for everything chronologically while still finding project-relevant items under each project.

The full depth of the routing brain — dual-path sync from the recorder, the Plaud API fallback, the offline transcriber bench — is its own case study in Voice-to-Action Pipeline. This page is about the wrapper that pulls it all together.

Component 3 — PWA on iPhone (one-tap capture)

The dashboard is a Progressive Web App. Add to Home Screen once, and it gets its own icon, its own splash screen, opens without the Safari chrome, and remembers the basic-auth credentials. From the lock screen, capture is two taps: home-screen icon → Quick Notes card → type → submit. That friction budget is what makes the system actually used.

The one PWA gotcha worth flagging: the service worker caches aggressively by default, and an update to the dashboard on the server would silently keep rendering the old version on the phone. The fix is a versioned cache name in the service worker (dashboard-vN) plus self.skipWaiting() on install and clients.claim() on activate — bump the version on every deploy, force the new SW to take over immediately, and the next open shows fresh content.

Component 4 — Sync Layer + Daily Cycle (backup and knowledge-base export)

Dropbox is the cross-machine persistence layer. The whole project tree lives in Dropbox; every routed note written on the Mac propagates to the MacBook Pro, the MacBook Air, and the Mac mini within seconds. Because notes are append-only markdown and project folders don't have multiple writers, there's no conflict logic to maintain.

Two daily crons on the Mac close the loop:

  • 2:00 AM — rsync backup. Mirror the Dropbox codebase tree to a 1 TB external drive. Incremental, ~17 GB working set, deletes removed files (mirror semantics). The backup log goes to ~/backup_dropbox.log; if the volume isn't mounted, that's the first thing I check in the morning.
  • 2:30 AM — Claude conversation knowledge-base export. Copy every .jsonl conversation from ~/.claude/projects/ into a per-machine folder under codebase/claude_knowledge_base/. One-way export, never syncs back. Incremental by file mtime + size, so a normal day adds ~1–5 MB. The intent is a personal corpus I can grep, RAG against, or fine-tune on later.

Both jobs are intentionally one-way mirror operations, not bi-directional sync. The principle: backups should not be able to corrupt the source.

Why It Works — Design Decisions Worth Defending

Why a $6/mo VPS instead of a free static-host (GitHub Pages, Netlify)? Because the queue needs a writable surface. The PHP endpoint that appends to queue/notes.md requires a real filesystem behind nginx. A static host can serve the dashboard but can't accept the POST. Six dollars a month is the cheapest writable HTTPS endpoint I could find that I also control end-to-end.

Why pull instead of push (cron instead of webhook)? A webhook would mean a public listener on the Mac — a tunnel, an open port, a new attack surface, a daemon to supervise. A 15-minute cron pulling a static file off a hardened nginx box has zero open ports on the private side, has no daemon, and its worst-case latency (15 minutes) is well inside my tolerance for “did the note land?” Pull beats push for personal infrastructure.

Why a markdown file as the queue? First-principles: a queue with one producer (the PHP endpoint) and one consumer (the cron) does not need broker semantics. curl, cat, and > file are the only operations. I can read it, edit it, audit it, replay it. If the cron fails the queue just stays full until the next run — nothing is lost, nothing crashes, no deadlock to debug.

Why Claude as the router instead of regex rules? I started with regex. It broke the first time someone said “Cap Group” instead of “Capital Group,” and harder when a transcript said “Brian” but meant “Ryan” (a homophone Plaud produces reliably). Claude is a good-enough fuzzy classifier with built-in error correction, and the prompt is editable in 30 seconds. The cost per run is fractions of a cent. The total cost of running this for a year is less than one Otter.ai monthly subscription.

Why Dropbox at all — isn't the mesh VPN enough? The mesh connects my machines but doesn't deal with offline edits or file history. Dropbox gives me version retention (recovery from accidental delete) and a transparent conflict resolver for the rare moments two machines touch the same file. The mesh gives me a private control plane (SSH, the cron's pull path). They solve different problems.

What I Learned

The headline lesson, and the one I keep coming back to: static HTML + cron + a markdown queue is enough infrastructure for a personal OS. The temptation, when you can build anything, is to build everything — a real database, a real API, a real worker queue. For one user, those choices actively hurt: more moving parts, more upgrade pain, more failure modes. Three static files and one PHP endpoint have run for over a year with a single restart.

Second: pull beats push when you control both ends. Every time I've been tempted to add a webhook to this system, I've regretted the design. A scheduled pull from a static file is easier to reason about, easier to debug, and easier to firewall than any push alternative. The 15-minute latency is below my psychological threshold for “did the thing happen,” and the operational simplicity is worth far more than the seconds saved by going push.

Third: the cheap writable HTTPS endpoint is a keystone. Once you have a $6/mo box that can append to a file, a surprising number of personal-tool ideas become trivially buildable. The dashboard, the notes queue, the Quick Notes PWA, the daily backup reporter — they all exist because the VPS exists. It's the single piece of “real infrastructure” in the system, and it pays for itself ten times over.

Fourth, and the one I'd underscore for anyone copy-pasting this design: own the corpus. Every routed note, every transcript, every daily export is sitting in my Dropbox tree as plain markdown. I can grep it, version it, feed it into a personal RAG, ship it to a fine-tune later. None of that is available to a Notion or Otter user. The corpus is the moat — the pipeline just feeds it.

Tech Stack

Public plane: $6/month cloud droplet, Ubuntu, nginx, Let’s Encrypt TLS, HTTP basic auth, one PHP endpoint, static HTML dashboard, manifest.json + service worker + icon set as a PWA. Private plane: always-on Mac mini behind a mesh VPN (Tailscale), bash + cron (15-min routing, 2:00 AM backup, 2:30 AM KB export), Claude CLI as the routing brain, markdown files as queue + prompt + output. Sync plane: Dropbox (4-machine propagation + version history), rsync to a 1 TB external drive (mirror backup), one-way JSONL export to a per-machine knowledge-base folder. Inputs: iPhone PWA Quick Notes card, Plaud transcripts (see Voice-to-Action Pipeline), Google Calendar pull.
