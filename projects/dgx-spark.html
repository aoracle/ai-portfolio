Self-Hosted LLM Cluster on 2× NVIDIA DGX Spark

A two-node GB10 Grace Blackwell cluster wired with 200 Gb/s fabric, running distributed vLLM + Ray inference on hardware I own — so the models, the data, and the latency are mine, not a metered API.

On-Prem LLM Inference 2× DGX Spark (GB10) 200 Gb/s Fabric vLLM + Ray (TP=2) NVFP4 Quantization

Cloud LLM APIs are excellent and I use them daily. They are also a metered hose: cost compounds with usage, every prompt leaves my machine, and the interesting part — how inference actually runs — stays behind someone else's endpoint. I wanted the capable models here, on my desk, running on silicon I control, with my trading data never leaving the LAN. So I stood up a two-node NVIDIA DGX Spark cluster, linked them at 200 Gb/s, and worked through the unglamorous plumbing required to actually serve a modern model across both of them. This is that system.

The Problem I Was Solving

Three things pushed me toward owning the inference layer. First, cost shape: my trading research and agent loops fire a lot of tokens, and per-token pricing that looks trivial on a demo becomes the line item that matters at volume. Second, data residency: a meaningful slice of what I want a model to reason over — positions, flow, proprietary signals — shouldn't have to leave my network to be processed. Third, understanding: I am suspicious of infrastructure I depend on but can't see inside. Running the full stack — fabric, NCCL, quantization format, serving runtime, tool-call parser — is the only way to actually learn where the sharp edges are.

The NVIDIA DGX Spark (GB10 Grace Blackwell, 128 GB unified memory) made it concrete. Two of them on a LAN, connected by ConnectX-7 fabric, is a real little datacenter. The question became: what does it take to serve a capable model across both nodes, correctly, with agent tool-use on top? The answer turned out to be about 10% model and 90% plumbing — exactly the lesson I came for.

System Architecture

Three machines: a MacBook Pro as the dedicated controller (where I work, where the editor and SSH client live), and two DGX Spark nodes forming the GPU cluster. The nodes are linked by a 200 Gb/s ConnectX-7 fabric brought up by NVIDIA's Sync Cluster Assistant. Models are served with vLLM, distributed across both nodes by Ray at tensor-parallel = 2, and an OpenCode agent layer talks to the resulting OpenAI-compatible endpoint.

Two DGX Spark nodes (dark) form the cluster; the controller orchestrates over the LAN. vLLM + Ray split each model across both nodes at tensor-parallel = 2; an OpenCode agent layer consumes the endpoint.

The Hardware

Two NVIDIA DGX Spark units, each a GB10 Grace Blackwell SoC with 128 GB of unified memory (note: nvidia-smi reports [N/A] for memory on GB10 because it's unified, not discrete VRAM — normal, not an error). They run DGX OS / Ubuntu 24.04, driver pinned at 580. The two nodes are joined by a 200 Gb/s ConnectX-7 fabric (CX7) that NVIDIA's Sync Cluster Assistant stands up — it handles the fabric bring-up and node-to-node SSH. Everything is headless and survives reboots. The MacBook Pro is the dedicated controller; I never run the cluster from a node's attached monitor.

The Serving Stack

The serving runtime is vLLM, run from NVIDIA's NGC container, with Ray orchestrating the two-node distributed serve at tensor-parallel = 2. NCCL and GLOO are pinned to the fabric interfaces (NCCL_SOCKET_IFNAME, GLOO_SOCKET_IFNAME), InfiniBand disabled in favor of the Ethernet fabric, and the head node starts the Ray cluster while the worker joins over SSH. The endpoint is OpenAI-compatible, which is what lets any agent framework plug in without modification.

# head node (spark1) — starts Ray + serves the model across both nodes
docker run -d --name ray-head --gpus all --network host --ipc host \
  -e NCCL_SOCKET_IFNAME=enp1s0f0np0 -e GLOO_SOCKET_IFNAME=enp1s0f0np0 \
  -e NCCL_IB_DISABLE=1 -e VLLM_HOST_IP=<head-fabric-ip> \
  -v /models:/models:ro nvcr.io/nvidia/vllm:26.05-py3 \
  bash -c "ray start --head --port=6385 --num-gpus=1 && sleep 55 && \
    vllm serve /models/<MODEL> --tensor-parallel-size 2 \
    --gpu-memory-utilization 0.5 --max-model-len 32768 \
    --enable-auto-tool-choice --tool-call-parser hermes"

The Model-Selection Journey (the real engineering)

This is where the time went, and it's the part worth documenting. Serving a model is easy; serving a capable model on brand-new silicon (GB10) is a moving target. The path:

  • vLLM 0.19 failed on modern models. Tokenizer/arch errors on current Qwen and DeepSeek releases — the runtime hadn't caught up to the model formats yet.
  • Never serve a GGUF on vLLM 0.19. Its experimental GGUF loader silently corrupts weights — the server starts, returns output, and the output is garbage. Confirmed on Qwen2.5-72B-Q4 at both TP=2 and TP=1, so it isn't a parallelism bug. Use llama.cpp (llama-server) for GGUF; it serves them correctly.
  • The capable-model path (found after real digging): NGC nvcr.io/nvidia/vllm:26.05-py3 — vLLM 0.20.1 + transformers 5.6.0 — serves Qwen3.6-35B-A3B-NVFP4 correctly on GB10: coherent, ~13 tok/s, NVFP4 quantization. The right runtime version was the unlock, not a newer one.
  • Tool-call parsers are per-model. Qwen2.5 emits the Hermes format (––tool-call-parser hermes); Qwen3.6 emits XML <function=...> blocks (––tool-call-parser qwen3_coder). Get this wrong and agents get 400 auto tool choice requires... or silently never call tools.
  • Long context via YaRN. Pushing past training context needs --rope-scaling yarn with careful JSON (the docker bash -c wrapper is fragile), plus Qwen-specific --override-kv qwen2.context_length=int:131072 or vLLM caps at training length.

Throughput on the cluster today: ~13 tok/s on the 35B NVFP4 model, ~10 tok/s on the 32B coder at 128k context. Bigger targets (Llama-3.3-70B-NVFP4, DeepSeek-V4-Flash at W4A16 with 1M context) are projected around ~1800 tok/s prefill / 40 tok/s generation once the vLLM 0.22 line is stable on GB10.

Agent Layer on Top

A model is only useful if something drives it. I run OpenCode as the agent loop on the head node, pointed at the cluster's OpenAI-compatible endpoint. Generation and agentic bash tool-use are both verified end-to-end in-window. The one open edge: reasoning models (Qwen3.6 is a thinking model) make the agentic tool-execution loop unreliable — with the reasoning parser on, the agent waits on content while vLLM streams reasoning_content and hangs; without it, the model narrates and skips the tool call. Raw generation and curl-level tool calls work today; closing that agent loop is the next milestone.

Why It Works — Design Decisions

  1. Own the hardware. No per-token tax, no data egress, no rate limits, no model deprecations I didn't choose. The cluster is a fixed cost that gets cheaper every time I use it.
  2. NVFP4 to fit capability in 128 GB. A 70B-class model doesn't fit one Spark at full precision; NVFP4 quantization is what makes a capable model servable on this hardware at useful throughput.
  3. Ray for multi-node tensor parallelism. Two single-node serves would have been simpler but would cap model size at what fits one 128 GB unit. TP=2 across the fabric doubles the addressable memory and is the whole point of clustering.
  4. Reproducible, not one-off. Every working configuration is captured as a versioned serve script + a validated-recipe doc, so bringing the cluster back after a driver update or a model swap is a known procedure, not an archaeology project.
  5. Honest about the frontier. I document what works and what doesn't (GGUF-on-vLLM corruption, the reasoning-agent loop). The gotchas are the most valuable output of the project; hiding them would make it marketing, not engineering.

What I Learned

The headline lesson: distributed inference is 10% model and 90% plumbing. The model is a file. The hard, interesting work is NCCL over a fabric, picking the quantization format the runtime actually supports, matching the tool-call parser to the model's emission format, and pinning driver/runtime versions that haven't drifted past each other. None of that is visible from an API.

Second: the quantization format and the serving runtime are a coupled pair. A model that "works" on paper (right size, right license) is useless if your runtime silently mangles its weights in that format. You find out by reading the output, not the startup log.

Third, and the one I'm still working on: the agent loop is the real frontier, not raw generation. Getting tokens out of a local model is a solved problem. Getting a reasoning model to reliably execute a tool call inside an agent loop — where the runtime streams reasoning_content the agent doesn't know to wait on — is where the next real work is.

Tech Stack

Hardware: 2× NVIDIA DGX Spark (GB10 Grace Blackwell, 128 GB unified memory each) + MacBook Pro controller. Networking: ConnectX-7 200 Gb/s fabric, NVIDIA Sync Cluster Assistant, LAN over Ethernet. Serving: vLLM (NGC container, 0.20.1), Ray (distributed, TP=2), Docker, NCCL/GLOO, llama.cpp for GGUF. Models: Qwen3.6-35B-A3B (NVFP4), Qwen2.5-Coder-32B, with Llama-3.3-70B-NVFP4 and DeepSeek-V4-Flash as targets. Quantization: NVFP4 (primary), W4A16, GGUF Q4 (via llama.cpp). Agent layer: OpenCode with hermes / qwen3_coder tool-call parsers. OS: DGX OS / Ubuntu 24.04, driver pinned at 580.
