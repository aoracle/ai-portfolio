Voice-to-Action Pipeline

From a $200 voice recorder to routed action items in the right project folder, no human in the loop — a 15-minute cron, two sync paths, and one Claude prompt do the rest.

15-min Cron Dual-path Sync Multi-project Routing Claude-orchestrated Offline-first Fallback

I record meetings. Then what? For most people, the recording becomes a 90-minute MP4 they will never open again. For me, it becomes a markdown file in the right project folder within 30 minutes — classified, summarised, and with action items extracted — without me touching a keyboard between the recording stopping and the file landing. This case study walks through how that pipeline is built: a Plaud voice recorder on one end, three Python scripts and a shell script in the middle, and Claude as the routing brain at the back.

The Problem I Was Solving

I run multiple parallel workstreams. Some are consulting engagements with their own jargon and their own ticket numbers. Some are family-side projects with their own document trails. Each one generates voice context every week — standups, design discussions, phone calls with lawyers, conversations with my parents. A recording-to-text tool is necessary but nowhere near sufficient. The transcript itself is just more raw material. The real question is: where does the transcript belong, and what does it commit me to do next?

I tried Otter.ai first. It transcribes, but it does not route, it does not extract action items into my file system, and it puts my meeting corpus on someone else's servers behind an account I do not own. I did not want a SaaS island. I wanted a pipeline that ended in markdown files inside my Dropbox tree, named the way I name files, organised the way I organise projects, summarised in the categories I care about. The transcript service is a commodity; the routing is the value.

The constraint that drove the design: no manual step between recording and a usable artifact. If I have to open a web app, copy a transcript, paste it somewhere, pick a project, and click save, I will not do it — not after the fourth meeting of the day. The whole pipeline has to run on a cron without me.

System Architecture

The pipeline has four stages, each isolated from the next by a flat file or a folder. There is no message bus, no webhook, no worker queue. Every handoff is a directory on disk or a markdown file:

┌──────────────────────────────────────────────────────────────┐
│  STAGE 1 — Capture                                           │
│  Plaud voice recorder (carried in pocket)                    │
│    • Hardware button → record                                │
│    • Audio uploaded to Plaud cloud                           │
│    • Plaud's service transcribes + diarises (speaker turns)  │
└──────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────┐
│  STAGE 2 — Sync (dual-path)                                  │
│                                                              │
│  PRIMARY:  Plaud → Google Drive ("Plaud Transcripts" folder) │
│            fetch_from_google_drive.py  (OAuth, no token)     │
│                                                              │
│  BACKUP:   Plaud REST API (api.plaud.ai)                     │
│            fetch_transcripts.py  (bearer token, ~10mo TTL)   │
│                                                              │
│  Both write to:  ANAND/inbox/plaud/YYYY-MM-DD_HH-MM_*.md     │
└──────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────┐
│  STAGE 3 — Routing brain (every 15 min)                      │
│  notes_processor/process_notes.sh on the Mac                 │
│    1. Pull queue from public dashboard                       │
│    2. Bail if empty                                          │
│    3. Pipe queue + PROMPT.md → claude --print                │
│    4. Clear remote queue on success                          │
└──────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────┐
│  STAGE 4 — Project folders (the payoff)                      │
│    INN/notes/YYYY-MM-DD.md         (Capital Group work)      │
│    TTT/notes/sap/YYYY-MM-DD.md     (UNFI / SAP)              │
│    TTT/notes/data_engineering/...  (UNFI / DE)               │
│    BAMPFA/notes/YYYY-MM-DD.md      (museum project)          │
│    cars180/notes/YYYY-MM-DD.md     (side project)            │
│    ANAND/notes/voice/YYYY-MM-DD.md (personal log, always)    │
└──────────────────────────────────────────────────────────────┘

The intentional choice at every boundary is to use a flat file or a folder instead of a service. The sync state is a JSON file. The queue is a markdown file. The prompt is a markdown file. The destination is a directory. If anything breaks, the failure point is one of three Python scripts or one shell script — not a vendor outage, not an expired webhook, not a queue that drained without me knowing.

Component 1 — Capture: Why a Hardware Recorder

I carry a Plaud recorder. Single physical button. The reason it beats a phone app: the phone is a hostile environment for capture. Notifications interrupt. Battery drains. iOS revokes mic access in the background. A dedicated device with a physical record button is more reliable and lower-friction than any app, and it never makes me unlock a screen mid-conversation. The recorder mirrors audio to Plaud's cloud, where their backend runs transcription with speaker diarisation. That part I outsource — I have no edge over Plaud at making mel-spectrograms.

I also keep an offline transcriber bench-ready in a separate folder (offline-transcriber/) built around Vosk — small model (40 MB) for real-time, large model (1.8 GB) for accuracy. It is not in the production pipeline today; it is my insurance policy. The day Plaud sunsets their cloud, or the day I want to transcribe a meeting that should never touch a third-party server (legal calls, family medical), I have a fully offline path ready:

# offline-transcriber/testing/file_transcribe.py (excerpt)
model = Model("models/vosk-model-en-us-0.22")
rec = KaldiRecognizer(model, wf.getframerate())
rec.SetWords(True)

while True:
    data = wf.readframes(4000)
    if len(data) == 0: break
    if rec.AcceptWaveform(data):
        results.append(json.loads(rec.Result()))

final = json.loads(rec.FinalResult())

Vosk runs locally on a CPU, no GPU required. Output includes word-level timing, which lets me emit SRT subtitles for video review. The decision to keep an offline path warm, even though I do not use it day to day, is itself the lesson: vendor risk is a real risk for personal infrastructure, and the cost of a fallback is one folder of code I keep maintained.

Component 2 — Dual-Path Sync (the most important design decision)

The transcript has to land in ANAND/inbox/plaud/ on my Mac. There are two ways to get it there, and I run both:

Primary path — Google Drive. Plaud has a setting to mirror new transcripts into a chosen Google Drive folder. I created Plaud Transcripts in my Drive, point Plaud at it, and a Python script (fetch_from_google_drive.py) polls the folder using the same Google OAuth credentials I already use for Calendar sync. No second token to manage. The script keeps a drive_sync_state.json file that maps Drive file IDs to their last-modified timestamps, so it only downloads new or updated transcripts:

# fetch_from_google_drive.py (excerpt)
query = f"'{folder_id}' in parents and trashed=false"
results = service.files().list(
    q=query,
    orderBy='modifiedTime desc',
    fields='files(id, name, mimeType, modifiedTime, createdTime)',
).execute()

for file in results.get('files', []):
    if file['id'] in synced_files \
       and synced_files[file['id']] == file['modifiedTime']:
        continue   # already pulled, skip
    download_file(service, file['id'], file['name'])
    synced_files[file['id']] = file['modifiedTime']

Backup path — Plaud REST API. If the Drive integration breaks (Plaud changes their export, Zapier mapping drifts, Drive folder accidentally renamed), I do not want to be stuck. fetch_transcripts.py talks directly to api.plaud.ai with a bearer token I copy out of the web app's localStorage (plaud_token.txt, ~10-month TTL). It hits /file/simple/web for the file list, then /file/detail/{id} for the signed S3 URLs that hold the transcript JSON, ungzips the payload, and writes the same markdown format the Drive path produces:

# fetch_transcripts.py (excerpt)
def get_headers(token):
    return {
        "Authorization": f"bearer {token}",
        "Accept": "application/json",
        "Origin": "https://web.plaud.ai",
    }

resp = requests.get(f"{API_BASE}/file/simple/web",
                    headers=get_headers(token),
                    params={"skip": 0, "limit": 50,
                            "is_trash": 2,
                            "sort_by": "start_time",
                            "is_desc": "true"})
files = resp.json().get("data_file_list", [])

for f in files:
    detail = requests.get(f"{API_BASE}/file/detail/{f['id']}", ...).json()
    transcript_url = next(item["data_link"]
                          for item in detail["data"]["content_list"]
                          if item["data_type"] == "transaction")
    data = gzip.decompress(requests.get(transcript_url).content)
    transcript_text = format_transcript(json.loads(data))

Why both? Because the cost of writing the second path once is small, and the cost of being blocked on Friday evening because the only path failed is large. Both write into the same inbox, both maintain their own sync-state JSON, and either one can be the only one running for weeks without the other noticing.

Each transcript lands as YYYY-MM-DD_HH-MM_Meeting_Title.md with a YAML-ish header (date, duration, source, ID), an optional summary block from Plaud's auto-summary, and the full transcript with timestamps and speaker labels:

# 2026-05-28 14:02 Capital Group standup

**Date:** 2026-05-28 14:02
**Duration:** 28m 14s
**Source:** Plaud

---

## Transcript

[00:02] **Speaker 1**: Let's start with the IPAC silver layer review...
[00:18] **Speaker 2**: I pushed the DBT changes last night, ticket IPAC-12891...

Component 3 — The Routing Brain

Now the interesting part. A transcript sitting in inbox/plaud/ is not yet useful. I need it classified into the right project folder, with action items extracted, with the noise filtered out (Plaud records continuously, so 70% of any transcript is background café chatter and small talk). This is where Claude earns its keep.

A 15-minute cron on the Mac runs a single shell script (process_notes.sh) that does four things in sequence:

# notes_processor/process_notes.sh (essence)
QUEUE_URL="https://<my-domain>/queue/notes.md"
QUEUE_LOCAL="$SCRIPT_DIR/inbox/notes_queue.md"

# 1. Pull queue from public dashboard
curl -s "$QUEUE_URL" -o "$QUEUE_LOCAL"

# 2. Bail if empty (don't burn tokens)
[ -z "$(cat "$QUEUE_LOCAL" | tr -d '[:space:]')" ] && exit 0

# 3. Hand off to Claude with our routing prompt
"$CLAUDE_BIN" -p "$(cat "$PROMPT_FILE")" \
  --dangerously-skip-permissions 2>&1 | tee -a "$LOG_FILE"

# 4. Clear remote queue only on success
if [ $? -eq 0 ]; then
    ssh root@<my-vps> "> /var/www/dashboard/queue/notes.md"
fi

The cron is dumb on purpose. All the intelligence lives in PROMPT.md, which I can edit without redeploying anything. The prompt itself is a documented decision tree. Here is the noise filter:

# PROMPT.md — Step 2: Filter Noise

Plaud records continuously, so transcripts contain background noise. IGNORE:
- Random background conversations (store clerks, strangers)
- Filler phrases: "I'm sorry", "Okay", "Thank you", "I don't know", "Music"
- Very short fragments under 10 words with no context
- Timestamps with no meaningful content after them
- Speaker 2/3/etc if they're clearly not me (background people)

KEEP only:
- Direct instructions starting with "ok this is personal" or "for TTT"
- Action items, reminders, ideas
- Meeting notes, follow-ups
- Family/personal plans, project-related thoughts

The classifier is keyword-based but interpreted by Claude, which means it handles fuzzy matches (Capital Group / "Cap Group" / "IPAC" all route to the same project) and resolves obvious transcription errors using a small name dictionary at the bottom of the prompt:

# PROMPT.md — Step 3: Project routing
| Context cue                                | Project    | Save to                          |
|--------------------------------------------|------------|----------------------------------|
| "ok this is personal"                      | Personal   | ANAND/notes/voice/YYYY-MM-DD.md  |
| "for TTT" or "TTT note"                    | TTT        | TTT/notes/YYYY-MM-DD.md          |
| "INN" / "Capital Group" / "IPAC" / "Ryan"  | INN/CG     | INN/notes/YYYY-MM-DD.md          |
| "cars180" / "car data"                     | cars180    | cars180/notes/YYYY-MM-DD.md      |
| "BAMPFA" / "museum" / "exhibition"         | BAMPFA     | BAMPFA/notes/YYYY-MM-DD.md       |
| (no cue)                                   | Personal   | ANAND/notes/voice/YYYY-MM-DD.md  |

# Known transcription errors to fix
| Transcribed     | Correct          |
|-----------------|------------------|
| Sneha           | Snehal (wife)    |
| Rehan / Ridhan  | Rayaan / Hridhaan|
| Ryan (in INN)   | Rayaan or Ryan?  | ← ambiguous, ask context

The output is deterministic: every note ends up in two places — the central voice log at ANAND/notes/voice/YYYY-MM-DD.md (always), plus the project folder if the routing matched something specific. The double-write means I can grep the voice log for everything chronologically while still finding project-relevant items under the project folder.

The queue itself can be populated two ways: (a) Plaud transcripts dropped into inbox/plaud/ get summarised and the summary line goes into the queue, or (b) I tap a Quick Note on the dashboard PWA from my phone, which POSTs to a PHP endpoint on my VPS that appends to queue/notes.md. Either way, the same routing brain handles it. The cron does not care where the queue line came from.

Why It Works — Design Decisions Worth Defending

Why not Otter.ai? Otter transcribes well. It does not route into my file system, it does not let me edit the classifier (the classifier is the value), and the corpus lives on their servers behind their account. The transcripts are mine in the loosest sense. With Plaud + Drive + my own routing, I own the artifacts in plain markdown on my disk.

Why dual-path sync? Because vendor lock-in is a tax I refuse to pay on my own infrastructure. Drive is the primary because it requires zero token management (Google OAuth is already set up for Calendar). The REST API is the backup because Plaud could change their Drive export tomorrow and I want to be untroubled when they do. The marginal cost of running both is a second Python script I rarely touch.

Why a 15-minute cron instead of webhooks? Pull beats push for personal infrastructure. A webhook means a public listener on my Mac, which means a tunnel, an open port, and a new attack surface. A cron pulling a static markdown file off a hardened nginx box is cheaper to reason about, has zero open ports, and the worst-case latency (15 minutes) is below my tolerance for "did that note land?"

Why a markdown file as the queue? Same first-principles reason a flat file beats Redis for a one-user system. A queue with no consumers and no producers other than me does not need broker semantics. curl, cat, and > file are the only operations. I can read it, edit it, audit it, replay it. If the cron fails, the queue does not disappear — it just stays full until the next run.

Why Claude as the routing brain instead of regex rules? I started with regex. It broke the first time someone said "Cap Group" instead of "Capital Group." It broke harder when a transcript said "Brian" but meant "Ryan" (homophone, common in Plaud transcripts). Claude is a good-enough fuzzy classifier with built-in error correction, and the prompt is editable in 30 seconds. The cost per run is fractions of a cent. The total cost of running this pipeline for a year is less than one Otter.ai monthly subscription.

Why a separate offline-transcriber folder I do not actively use? Because the day I need it, I will not have time to build it. Keeping Vosk warm with both small and large models downloaded, scripts that take a file path and return SRT/JSON/text, and a tested venv is cheap insurance.

What I Learned

The first principle behind the whole thing: the transcript is not the product. The routed, classified, action-extracted note in the right project folder is the product. Most voice-to-text tools optimise the transcription. The transcription is the easy part now — commodity, accurate, cheap. The hard part is everything downstream: classification, name correction, noise filtering, action extraction, routing, archival. That is where a thoughtful prompt and a 15-minute cron beat a $20/month SaaS hands down.

Second lesson: flat files are an underrated runtime. A markdown file as a queue. A JSON file as sync state. A markdown file as the prompt. A directory as the destination. None of these need a database. None of these need a server. They survive a Mac reboot, a Dropbox sync conflict, a Claude CLI upgrade. The simplest persistence layer that meets the requirement is almost always a file.

Third lesson: build the backup path the same day you build the primary. The marginal cost of writing the second sync script while the first one is fresh in my head was an afternoon. Writing it six months later, after the first one breaks, would cost a weekend and a lost transcript. The discipline is paid up front.

Fourth lesson: own your corpus. Every transcript I have ever recorded is sitting in my Dropbox tree as plain markdown, dated and named consistently. I can grep it. I can feed it into a personal RAG. I can run analytics. I can fine-tune on it eventually. None of that is available to an Otter user.

Tech Stack

Python 3 (sync scripts, classification helpers). Google Drive API + OAuth (primary sync path, scopes shared with Calendar integration). Plaud REST API + bearer token (backup sync path). Bash + cron (15-minute orchestration loop). Claude CLI (claude --print) as the routing brain. Markdown files as queue, prompt, transcripts, and output. Vosk (small + large English models) as the offline-first fallback transcriber. Dropbox as the cross-machine persistence layer.
